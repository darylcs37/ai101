Implementation Plan: From Vibe Code to Production-Grade AI Products

Overview

A production-grade AI product should be built as a gated delivery system, not as a straight line from prompt to deployment. The recommended stack is Claude for architecture and control definition, Cursor for implementation, scanners for codebase reality checks, NanoClaw for browser-level UX and auth-path validation, pentest-ai-agents for structured offensive testing, OpenMythos for targeted vulnerability assessment, and Runable plus CI for evidence-driven release gates.[1][2][3][4][5]

This operating model matches two current realities. First, NIST SSDF and its generative-AI extension emphasize secure design, review, testing, triage, and remediation as lifecycle practices rather than end-of-pipeline add-ons. Second, recent public work from AISLE, Anthropic, and Cloudflare shows that AI cyber capability is modular and system-driven, with real value emerging from orchestration across ranking, hunting, validation, proof generation, traceability, and reporting rather than from a single model prompt.[2][4][6][7][1]

Target operating model

The delivery system should have seven controlled lanes, each answering a different release question. Separating these lanes prevents one tool from being over-trusted and makes failure modes observable earlier.[7][1]

Lane Primary tool Main job Release question
Architecture Claude System design, trust boundaries, auth model, input contracts Are the controls specified? [1][8]
Implementation Cursor Product code, tests, migrations, adapters Was the design implemented? [2]
Code scanning Scanner stack Catch auth gaps, BOLA patterns, risky DB privilege use, dependency issues Does the codebase obviously violate policy? [9][8]
UI/UX validation NanoClaw Run login, onboarding, CRUD, and role-based browser journeys Does the product behave safely for real users? [3]
Offensive assessment pentest-ai-agents Structured API, web, logic, and LLM red-team testing against staging Can a real attacker exploit the running product? [5]
Static vulnerability assessment OpenMythos Targeted source-code analysis of risky paths and patch suggestions Are there deeper exploitable weaknesses in the code? [4][6][7]
Governance Runable + CI Evidence collection, gating, exceptions, sign-off Can this release be trusted? [1][2]

Phase 1: Architecture and control pack

Start with Claude, but use it to define controls rather than to generate large volumes of final code. Claude should produce a system context diagram, trust boundaries, role-action-resource matrix, endpoint inventory, input contract catalog, data-flow map, logging and observability requirements, rollback constraints, and abuse-case list.[8][10][1][2]

The control pack should explicitly define authentication, authorization, and input validation because these remain the highest-probability weak points in fast AI-generated application code. OWASP guidance stresses that authorization must be validated on every request, BOLA occurs when object identifiers are trusted without proper object-level checks, and input validation must happen server-side as early as possible with allowlisting and semantic validation, not just UI-side checks.[9][10][8]

Required Claude artifacts

  • Architecture decision record for the chosen stack and trust boundaries.[1]
  • Endpoint inventory labeled public, authenticated, admin, service-only, or internal.[8]
  • Role matrix covering user, admin, service account, and tenant or org scope.[8]
  • Input contract pack with type, length, enum, regex, normalization, and semantic rules per field.[10]
  • Abuse cases covering auth bypass, BOLA, file upload misuse, prompt injection entry points, secret exposure, and session expiry behavior.[11][9]
  • Security acceptance criteria for every story, including tests and evidence expected later in CI.[2][1]

Phase 2: Cursor implementation under constraints

Cursor should implement against the control pack, not replace it. External guidance on secure AI-assisted development consistently points toward mandatory review, secure defaults, and gated testing before AI-generated code is treated as production ready.[2]

A practical rule is that no route, server action, mutation, parser, or privileged job reaches the main branch unless it includes an auth decision, validation schema, logging behavior, ownership semantics where relevant, and at least one misuse-path test for the highest-risk flows. That rule turns "vibe coding" into constrained implementation rather than free-form generation.[9][10][8]

Cursor coding rules

  • No new endpoint without explicit auth middleware or dependency-injection guard.[11][8]
  • No object fetch, update, or delete without object-level authorization logic to prevent BOLA.[9]
  • No new user input path without server-side validation and clear error handling.[10]
  • No secrets in code, prompts, test data, or environment templates.[1][2]
  • No broad dependency additions without review and version discipline.[2]
  • No merge without unit tests, integration tests, and misuse-path coverage for high-risk features.[1][2]

Phase 3: Scanner lane for codebase reality

The scanner lane should run immediately after implementation and before browser or offensive testing. Its purpose is to detect what is actually present in the codebase, not what the architecture intended. This matters especially for missing auth checks, BOLA indicators, and privilege configuration drift.[8][9]

The scanner stack should combine SAST, dependency scanning, secrets scanning, IaC scanning, and custom grep or AST rules tuned to your stack. The highest-value custom rules are the ones that check whether routes are missing auth guards, whether user-controlled IDs reach database operations without ownership predicates, and whether privileged data-layer constructs appear without review.[9][8]

Scanner outputs

Bucket Examples Action
Route findings Missing auth middleware, missing session checks, public write route Fix or explicitly allowlist. [8][11]
Query findings Direct object lookup without ownership check, missing tenant filter Treat as likely BOLA until disproven. [9]
Database findings RLS gaps, risky privilege boundaries, broad service-role usage Manual review and least-privilege remediation. [8]

Merge policy should fail shut for critical findings. Unresolved criticals block release, while accepted risks require written rationale, approver sign-off, and a remediation due date.[1][2]

Phase 4: NanoClaw UI and UX validation

NanoClaw's documented browser capability is Playwright-based and supports navigation, snapshots, form filling, clicking, screenshots, data extraction, file uploads, PDFs, and saved authentication state. That makes it well suited to browser-level validation after code scanning but before release approval.[3]

Its best role is deterministic execution of high-value journeys rather than broad exploratory fuzzing. Use it to validate login, onboarding, CRUD, role-based navigation, direct URL access attempts, error-state clarity, and session-expiry behavior using reusable auth states and evidence artifacts such as screenshots and extracted text.[3]

Golden NanoClaw journeys

  • Standard-user login success and invalid-login rejection.[3]
  • New-user onboarding flow including validation copy and progress behavior.[3]
  • CRUD smoke tests for core entities with screenshots after create, read, update, and delete.[3]
  • Role-diff tests comparing standard-user and admin navigation visibility and direct-path access.[3]
  • Unauthorized object access attempts using manipulated identifiers to reveal BOLA symptoms in real UI flows.[9][3]
  • Session-expiry and stale-session handling tests for redirects, safe failure states, and data leakage checks.[3]

Browser-level evidence matters because code that passes static scanners can still fail in hidden-but-reachable routes, broken redirects, unsafe deep links, or unusable validation states. NanoClaw closes that gap by exercising the product as a user would experience it.[3]

Phase 5a: pentest-ai-agents as structured offensive coverage

pentest-ai-agents provides a structured offensive layer that should sit before OpenMythos's code-level analysis. Its 35 Claude Code subagents cover planning, recon, offensive operations, detection, and reporting, and they integrate naturally into a product-security workflow where staging systems are in scope for authorized testing.[5]

The relevant product-security subset is smaller than the full collection. api-security, web-hunter, bizlogic-hunter, vuln-scanner, llm-redteam, cicd-redteam, detection-engineer, and report-generator are the main agents to operationalize. The framework also distinguishes Tier 1 advisory agents from Tier 2 agents that can compose and execute commands after scope declaration and approval.[5]

High-value agents for AI products

  • api-security: exercises REST, GraphQL, and WebSocket paths against OWASP API risk patterns, including JWT and OAuth issues.[5]
  • bizlogic-hunter: targets workflow bypass, BOLA, authorization flaws, and race conditions that scanners often miss.[5]
  • llm-redteam: targets prompt injection, RAG poisoning, tool abuse, and MCP server exploitation using tooling aligned to OWASP LLM Top 10 and MITRE ATLAS.[5]
  • report-generator: turns validated results into remediation-ready pentest output.[5]

pentest-ai-agents also includes a persistent findings database with export and handoff support, which maps well to Runable evidence artifacts and staged-release packets.[5]

Phase 5b: OpenMythos vulnerability assessment

OpenMythos should be positioned as a targeted vulnerability-assessment engine inside a broader harness, not as a self-sufficient oracle. AISLE's analysis argues that current AI cyber capability is modular, with scanning, detection, triage, patching, and verification functioning as a system rather than a single-model trick. It also argues that smaller and open models can do meaningful detection work when the surrounding system handles ranking, evidence capture, and validation.[4]

Anthropic's Mythos Preview results make that lesson concrete. In their published assessment, the scaffold autonomously found a 27-year-old OpenBSD TCP bug, a 16-year-old FFmpeg integer mismatch, a 17-year-old FreeBSD NFS remote code execution issue, Linux kernel privilege-escalation chains, and browser JIT heap-spray vulnerabilities across major browsers after only an initial prompt and then independent iterative work.[6]

Reusable harness design

The core Anthropic workflow is directly reusable for OpenMythos: launch isolated containers with the source code, rank files by attack surface, run many short-context parallel agents on the highest-risk files, and send each candidate bug report to a separate verification layer before a human sees it. Anthropic reported that expert contractors agreed exactly with the model's severity in 89% of 198 manually reviewed reports and were within one severity level in 98% of cases, which is a useful calibration target for your own verification harness.[6]

Vulnerability classes to prioritize

  • Memory-safety boundaries, including unsafe Rust, JNI, ctypes, C, and C++ pointer-heavy code.[6]
  • Parser and codec entry points where integer mismatches and sentinel collisions can hide for years.[6]
  • Network authentication handlers and packet-processing logic.[6]
  • Cryptographic implementation logic around key, certificate, session, and protocol handling.[6]
  • Web-application logic where implemented behavior diverges from intended auth, BOLA, or workflow policy.[9][6]

File-ranking scoring rubric

Before parallel assessment agents run, a ranking pass should assign each file a 1 to 5 priority score based on attack surface. This mirrors Anthropic's documented scaffold and is one of the easiest high-impact upgrades to make reusable.[6]

<>Skip. [6]
Score Label Canonical examples CI action
1 No surface Constants, enums, auto-generated schema files, pure type definitions, i18n strings
2 Minimal Internal utility functions, formatting logic, in-memory helpers Low priority. [6]
3 Moderate Business logic between validated layers, ORM models, migrations, internal service calls Queue. [6]
4 High Auth middleware, session management, authorization checks, file upload, admin routes, query builders, deserialization paths Prioritize. [6]
5 Critical Network parsers, protocol implementations, public handlers for user-controlled IDs, crypto primitives, memory-unsafe operations, sandbox boundaries, SSO callbacks, external-data ingestion Immediate. [6]

Only score 4 and 5 files should enter the first assessment wave. Score 3 files can join lower-priority nightly passes, while scores 1 and 2 are usually skipped entirely.[6]

Verification agent design

After assessment agents emit findings, a separate verification agent should receive each candidate report and attempt to confirm whether it is real, reachable, and worth escalating. That prompt should force four tasks: a reality check, a severity rating, a false-positive screen, and a structured JSON output containing confirmed, severity, real_and_reachable, reasoning, escalate_to_human, suggested_fix_class, and false_positive_reason.[6]

This verification layer matters because AI models remain capable of strong sensitivity on vulnerable code while still producing noisy or hedged findings on safe or patched code. The verification step should reject findings that rely on impossible preconditions, affect test-only code, require already-privileged attackers with no escalation path, or merely restate best-practice gaps without an exploit path.[7][6]

CI integration for nightly OpenMythos runs

The most practical CI pattern is a nightly scheduled workflow with four jobs: rank-files, assess with a matrix of parallel chunks, verify-and-triage, and gate. The assessment prompts should be per-file and short-context rather than monolithic, because both Anthropic and Cloudflare found that narrow, parallel tasks outperform one exhaustive agent session.[7][6]

All artifacts should be retained: ranked file manifest, chunk findings, verified findings, and Runable-ready evidence JSON. This makes every release auditable and gives security teams data to tune false-positive suppression and attack-surface coverage over time.[1][6]

Cost and throughput calibration

Anthropic published a useful cost benchmark: one thousand parallel runs against OpenBSD cost under $20,000 in aggregate, and the specific run that found the historical SACK bug cost under $50 in hindsight. The main lesson is not the exact number but the economics of parallel narrow hunts across ranked files rather than one expensive long-context pass over the whole codebase.[6]

Phase 5c: Cloudflare Project Glasswing lessons

Cloudflare's Project Glasswing offers the clearest published reference architecture for AI vulnerability assessment at scale against real production infrastructure. Over several months they pointed Mythos Preview at more than fifty internal repositories spanning runtime, edge data path, protocol stack, control plane, and open-source dependencies.[7]

Architectural lessons to copy

  • Mythos-class systems are qualitatively better at exploit-chain construction and iterative proof generation than general coding agents.[7]
  • Generic coding agents are the wrong shape for whole-repo vulnerability coverage because they saturate context quickly and cannot sustain enough hypotheses in parallel.[7]
  • C and C++ code generates more false positives than memory-safe stacks, which means language mix should influence queue design and reviewer staffing.[7]
  • Organic model refusals are inconsistent and cannot be treated as a reliable safety boundary. Harness-level controls are still required.[7]
  • Faster patching without architecture-aware regression and blast-radius control can ship fixes that are worse than the original bug.[7]

Cloudflare's six-stage harness

Cloudflare describes a harness with recon, hunt, validate, gapfill, dedupe, trace, and report stages, where the trace stage answers the most important question: whether attacker-controlled input actually reaches the bug from outside the system. Their design principles align closely with this report: narrow scope improves findings, adversarial review reduces noise, splitting different reasoning tasks across agents works better than bundling them, and many parallel narrow tasks outperform a single exhaustive agent.[7]

Phase 5d: llm-redteam prompt sequence for AI product features

For any feature that passes user-controlled text into model context, llm-redteam should run a structured prompt sequence against staging before release. This is essential for chat, search, summarization, document Q and A, code-generation copilots, agent tools, and MCP-server-connected experiences.[5]

Prompt sequence

  1. Threat-surface mapping: map where user-controlled input enters context, what system instructions are prepended, what tools or MCP servers are reachable, what data stores can be read or written, and what output channels exist.[5]
  2. Prompt-injection testing: attempt direct injection, indirect injection through retrieval or tool output, role override, context extension, encoding bypass, and delimiter-boundary attacks.[5]
  3. Sensitive-data exposure: test whether prompts can extract system instructions, secrets, internal paths, or cross-user data through retrieval or tool calls.[5]
  4. Excessive agency and tool abuse: attempt unintended tool calls, over-broad function invocation, chained tool misuse, MCP endpoint misuse, and unvalidated user-controlled tool parameters.[5]
  5. Insecure output handling: test whether model output can create stored or reflected XSS, query injection, command injection, or path manipulation when downstream components trust its output.[5]
  6. RAG poisoning: insert adversarial documents or retrieval content, trigger their retrieval, and observe whether they alter model behavior or override intended instructions.[5]
  7. Verification and reporting: emit structured JSON with severity, reproduction steps, OWASP LLM or MITRE ATLAS mapping, blast radius, and recommended mitigation for Runable ingestion.[5]

This sequence should be run against staging, not production, and tied to release criteria for any feature where the model can read privileged context, invoke tools, or produce output that downstream systems execute or render.[2][5]

Phase 6: Governance and release gates

Runable and CI should act as the control tower for the entire workflow. The release gate should be evidence-driven rather than trust-driven: architecture references, scanner results, NanoClaw artifacts, pentest results, OpenMythos findings, remediation status, known exceptions, rollback instructions, and approver sign-off should all be part of the release packet.[2][1][5]

Release criteria

A release should require all of the following:

  • All critical scanner findings resolved or explicitly excepted with senior approval.[1]
  • All golden NanoClaw journeys passing on staging.[3]
  • pentest-ai-agents findings triaged, with confirmed issues either remediated or accepted with rationale.[5]
  • OpenMythos high-confidence findings triaged and either remediated or disproven.[4][6]
  • Observability checks in place, including logs, metrics, traces, alert routing, and dashboards.[1]
  • Rollback documented and, ideally, rehearsed.[1]
  • Production config locked behind least privilege, branch protections, immutable CI templates, and reviewed deployment definitions.[2][1]

Operating cadence

Different controls should run at different speeds. Fast checks belong in the inner loop, broader analysis belongs in CI, and deeper offensive testing belongs in staging or scheduled nightly windows.[1][6][7]

Cadence Control Tooling
On save / pre-commit Lint, schema checks, unit tests, local scanner rules Cursor + local scanner
On PR SAST, secrets, dependency scan, auth/BOLA rules CI scanner stack [9][8]
On staging deploy NanoClaw golden journeys and role-path validation NanoClaw [3]
Nightly OpenMythos ranked-file assessment and drift scans OpenMythos harness [6]
Weekly or pre-release pentest-ai-agents offensive sweep, including llm-redteam for AI features pentest-ai-agents [5]
Pre-release Manual exception review, rollback validation, final Runable gate Humans + Runable [1]

Risk mitigation and remediation strategy

The main risk in vibe-coded delivery is over-trusting the model that generated the code or the model that reviewed it. The mitigation is to assume partial correctness and surround AI output with independent validation at every layer: design review, static scanning, browser execution, offensive testing, vulnerability triage, and governance gates.[4][2][7]

Risk Likely failure mode Primary mitigation Remediation
Missing auth Public or weakly protected route Auth matrix + scanner rule + route tests Add middleware or dependency guard and regression test. [8][11]
BOLA Object ID tampering reveals or mutates another user's record Ownership policy + query filter + NanoClaw direct-path test + bizlogic testing Add object-level authorization and deny-by-default logic. [9][3][5]
Weak validation Dangerous input reaches server logic Schema-first validation + server-side enforcement Centralize validators and add misuse-path tests. [10]
UI safety failure Hidden route still reachable, unsafe redirect, unclear failure state NanoClaw journeys and role-diff checks Fix navigation, redirects, and error copy. [3]
LLM prompt injection User or retrieved content overrides intended model behavior llm-redteam sequence + tool isolation + retrieval controls Harden prompts, isolate tools, add output encoding and RAG integrity controls. [5]
Vulnerability-assessment noise Team burns time on hedged or false findings Verification agent + trace stage + severity thresholds Suppress classes, improve prompts, and require independent confirmation. [6][7]
Unsafe AI patches Auto-generated fix changes behavior incorrectly Human review + tests + reassessment Minimize diff, add regression tests, and retain rollback path. [7]

30-60-90 day rollout

First 30 days

Define the Claude control pack, codify Cursor coding rules, deploy the first scanner rules, and stand up 5 to 10 NanoClaw golden journeys covering login, onboarding, CRUD, and role paths. Install pentest-ai-agents for staging-only use and start with api-security, bizlogic-hunter, and llm-redteam on one product surface.[3][5]

Use OpenMythos only on the highest-risk code categories in this phase so the team learns what good versus noisy findings look like. Standardize the Runable evidence packet now so later pipeline stages have a stable target.[4][6]

Days 31 to 60

Expand scanner coverage to more frameworks and database patterns, increase NanoClaw coverage, begin nightly OpenMythos runs against score 4 and 5 files, and operationalize weekly pentest-ai-agents sweeps for staging. Add severity-based merge policies and exception workflows so gates become enforceable rather than advisory.[6][5]

Days 61 to 90

Add AST-based scanner rules, tune false-positive suppression, add Cloudflare-style trace logic for high-confidence vulnerabilities, measure defect escape rate, and create dashboards for gate pass rates, remediation time, recurring vulnerability classes, and LLM-redteam findings by category.[1][7]

Success metrics

  • Percentage of new routes with explicit auth declaration at design time.[8]
  • Percentage of release candidates with zero critical scanner findings.[1]
  • NanoClaw pass rate on golden journeys and role-diff tests.[3]
  • pentest-ai-agents confirmed-findings rate after triage.[5]
  • OpenMythos precision after verification and trace.[7][6]
  • Mean time to remediate high-severity issues.[1]
  • Defect escape rate from staging to production for auth, validation, UI safety, and AI-feature abuse cases.[8][3][5]
  • Percentage of releases with complete evidence packets in Runable.[1]

Final recommendation

The most effective path from vibe code to production-grade AI products is not to slow AI coding down to traditional velocity, but to surround it with faster and independent control loops. Claude should define the system and controls, Cursor should implement within those guardrails, scanners should catch structural code issues, NanoClaw should verify browser behavior, pentest-ai-agents should test exploitability in the running product, OpenMythos should probe for deeper source-level vulnerabilities, and Runable plus CI should convert all of that into non-bypassable release gates.[4][3][7][1][5]

The winning system is not the smartest single model. It is the most disciplined workflow for converting partially trusted AI output into auditable, testable, and reversible software releases.[4][7]
